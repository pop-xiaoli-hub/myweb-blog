# 【iOS】启动优化

启动优化不是单纯地“让代码更快一点”，而是先理解 App 从点击图标到首屏出现，中间到底发生了什么。

这篇文章会从虚拟内存、Mach-O、pre-main 和 main 两个阶段入手，整理 iOS 启动的关键路径和优化点。

## 虚拟内存和物理内存

早期的数据访问是直接通过物理地址访问的，容易出现内存不够用、内存数据安全性差的问题。

为了更好地管理多个进程，系统在进程和物理内存之间增加了一个中间层，也就是虚拟内存。它本质上是一张虚拟地址和物理地址之间的映射表。

几个关键点：

- 每个进程都有独立的虚拟内存，地址从 `0` 开始，大小固定为 `4G`
- 每个虚拟内存会再被划分为一个个页，iOS 通常是 `16K`，其他平台常见 `4K`
- 进程之间无法直接相互访问彼此的虚拟内存
- 真正活跃的内容才会被按页加载到物理内存中，避免资源浪费
- 当 CPU 访问某个虚拟地址时，需要通过映射关系找到对应的物理地址
- 如果目标内容还没有被加载到物理内存，就会触发缺页异常，阻塞当前进程，等数据装载完成后再继续执行

按照这个机制，虚拟地址的起始位置和大小本来是固定的，安全性并不好。所以苹果引入了 ASLR 技术，也就是地址空间布局随机化。

ASLR 会让堆、栈、共享库等内存区域在每次启动时都有不同的基址，从而提升缓冲区溢出攻击的难度。但这也带来了一个结果：可执行文件和动态库在虚拟内存中的地址不是固定的，因此系统需要在加载过程中修正镜像中的指针，使它们最终指向正确位置。

可以简单理解为：

`正确的内存地址 = ASLR 随机地址 + 偏移值`

## 可执行文件和 Mach-O

不同操作系统的可执行文件格式并不相同。系统内核把文件读入内存后，会根据文件头判断它是什么格式，然后决定如何加载和执行。

在苹果平台里，最核心的可执行文件格式就是 Mach-O，也就是 Mach Object。

常见文件类型包括：

- `Executable`：可执行文件
- `Dylib`：动态链接库
- `Bundle`：运行时通过 `dlopen` 加载的动态库
- `Framework`：包含动态库、资源文件和头文件的集合

苹果还有一种通用二进制格式，也就是胖二进制。它会把多种 CPU 架构的 Mach-O 文件打包到一起，设备运行时根据自己的架构选择合适的那一份。

优点是兼容多架构，缺点是文件体积更大。

### Mach-O 结构

一个 Mach-O 文件通常可以分成三部分：

- `Header`：记录 CPU 架构、文件类型、加载命令数量等基础信息
- `Load Commands`：描述文件中数据如何组织，比如依赖了哪些动态库、入口地址在哪里、符号表位置在哪
- `Data`：真正的代码和数据内容，按段和节来组织

理解这些内容的意义在于：pre-main 阶段的大量工作，本质上都和 Mach-O 的装载、修正和链接有关。

## App 启动的定义

广义上的启动，是从点击图标到首页数据加载完成。

狭义上的启动，是从点击图标到启动图完全消失后的第一帧渲染完成。

通常更关注的是狭义启动时间，因为这直接影响用户对“App 打开是否够快”的感知。

启动的理想时间一般是 `400ms` 以内。因为从点击图标到显示 Launch Screen，再到 Launch Screen 消失，这个窗口本身就很短。如果启动耗时过长，用户会明显感觉到卡顿；如果启动时间超过 `20s`，系统甚至可能直接杀掉 App。

一个常见的启动耗时统计方式是：

- 起点：进程创建时间
- 终点：第一个 `CA::Transaction::commit()`

这里的 `CA::Transaction::commit()`` 是 Core Animation 提交事务的关键节点。像 `frame`、`bounds`、`alpha`、`transform` 这类界面改动，不会每次立刻刷到屏幕上，而是会在当前 RunLoop 即将结束时统一提交。

## 冷启动和热启动

启动通常分为两类：

- 冷启动：系统中没有当前 App 的进程缓存，例如重启手机后第一次打开 App
- 热启动：App 还保留着进程和部分运行状态，从后台重新回到前台

日常说的启动优化，默认主要是指冷启动优化，因为冷启动会完整走一遍装载和初始化流程，问题也更容易暴露出来。

## 启动流程概览

在 main 执行之前，系统已经做了非常多的工作。整个流程可以概括为：

> 点击 App -> 系统创建进程 -> 加载主 Mach-O 和 dyld -> dyld 接管启动 -> 加载依赖动态库 -> rebase、bind 修正符号 -> Objective-C runtime 注册类、方法、Category -> 执行 `+load`、constructor、C++ 静态初始化 -> 调用 `main()` -> `UIApplicationMain()` -> 首屏渲染

从启动优化的角度，可以把它拆成两个部分：

- `pre-main` 阶段
- `main` 阶段

## pre-main 阶段

pre-main 指的是 `main` 函数执行之前，操作系统和 dyld 完成的一系列装载、链接、修正和运行时初始化工作。

### 1. 加载动态库

系统会先从主文件的 Header 中读取依赖的动态库列表。dyld 根据这些记录去找到每个 dylib，并判断它是不是合法的 Mach-O 文件。

如果格式正确，系统会进一步校验代码签名，然后通过 `mmap()` 把对应的 segment 映射到进程的虚拟内存中。

这里有两个很关键的事实：

- 系统动态库通常来自 dyld shared cache，映射速度很快
- App 自带的动态库和第三方动态 Framework 需要从 App Bundle 中读取和映射，成本更高

而且一个 dylib 还可能继续依赖别的 dylib，所以 dyld 会递归地把整棵依赖树都加载完成。

这也是为什么“动态库数量过多”会直接拖慢启动。

### 2. Rebase 和 Bind

动态库被映射进来之后，还不能直接正常互相调用，因为各自目前只是“被放进了内存里”，很多地址和符号引用都还需要修正。

这个修正过程一般统称为 fix-ups，其中最核心的就是：

- `rebase`
- `bind`

因为 ASLR 的存在，镜像实际加载地址每次都可能不同，所以镜像内部那些依赖绝对地址的数据都需要重新定位，这就是 rebase。

而 bind 负责把符号引用真正绑定到目标实现上，比如某个类、某个方法、某个全局符号最终应该指向哪里。

现代编译器广泛使用位置无关代码，也就是 PIC。代码本身可以被加载到不同地址上运行，但其中很多调用最终还是要通过数据段里的指针间接跳转。dyld 在这里做的事，本质上就是把这些指针修正成正确值。

### 3. Runtime 注册和自动执行代码

在 Objective-C 工程里，pre-main 的耗时很大一部分还来自运行时初始化，包括：

- 注册类
- 注册方法
- 合并 Category
- 处理 selector、protocol 等元数据
- 执行 `+load`
- 执行 `__attribute__((constructor))`
- 执行 C++ 全局对象初始化

这一阶段的特点是：它们发生得很早，而且很多事情还发生在主线程上，所以只要堆得太多，就会直接拖慢首屏出现。

### pre-main 优化方向

#### 减少动态库数量

- 合并不必要的自有动态库
- 减少第三方动态 Framework 的数量
- 没有动态加载需求时，优先考虑静态链接

#### 减少 `__DATA` 段中的指针数量

对于 Objective-C 开发来说，Class、Method、selector、protocol、Category 等元数据最终都要进入 Mach-O 的 `__DATA` 段。

指针越多，dyld 做 rebase 和 bind 的成本就越高。

可以从这些方向入手：

- 合并分类和职责过于碎片化的类
- 删除无用的方法、类、Category、Protocol
- 控制过度动态化的设计

#### 减少 main 前自动执行代码

- 尽量少用 `+load`
- 更倾向使用 `initialize`、懒加载、`dispatch_once`
- 减少 `__attribute__((constructor))` 的使用
- 避免在 main 前做复杂逻辑和重任务

#### 不要过早创建线程

启动早期线程越多越好这件事并不成立。

线程的创建本身就有 CPU、内存和调度成本，过早地创建多个线程，反而可能引入锁竞争、主线程抢占和额外的上下文切换，影响首屏渲染。

## main 阶段

进入 `main` 之后，App 开始执行真正属于业务层的初始化流程。

这个阶段通常包括：

- 调用 `UIApplicationMain`
- 创建 `UIApplication`
- 启动主线程 RunLoop
- 配置 `UIWindow`
- 创建并展示根控制器
- 触发 `loadView`
- 触发 `viewDidLoad`
- 触发 `viewWillAppear`
- 首帧渲染后调用 `viewDidAppear`

如果是 iOS 13 及以后，通常还会走 Scene 生命周期，在 `scene:willConnectToSession:options:` 中配置窗口和根控制器。

### main 阶段优化方向

#### 延迟初始化非必要内容

不要在启动时一次性把所有东西都创建出来。能延迟的尽量延迟，特别是：

- 非首屏 `UIViewController`
- 非首屏模块
- 非必要 SDK
- 不影响首帧显示的视图和业务逻辑

#### 避免主线程重任务

启动阶段尤其要避免在主线程上做这些事情：

- 同步 I/O
- 网络请求阻塞
- 大 JSON 解析
- 图片解码
- 数据库操作
- 大量日志处理

这些工作如果不是首屏强依赖，就应该放到后台队列，并尽量安排在首帧渲染之后分批执行。

#### SDK 延迟初始化

很多 App 在启动时会初始化一大堆 SDK，但真正和首屏强相关的通常只有少数几个。

所以应该只保留启动必需的 SDK，把下面这些按需延后：

- 支付
- 分享
- 地图
- 广告
- IM
- 统计中的非关键链路

#### 优化首屏布局和资源

- 根控制器保持轻量
- 降低首屏视图层级复杂度
- 减少首帧前频繁 `updateConstraints` 和 `layoutSubviews`
- 保证 Auto Layout 约束关系稳定
- 控制首屏图片、字体、配置文件的大小
- 首屏必要资源尽量本地化、小体积化

## 启动优化总结

### pre-main

1. 减少动态库数量  
   合并不必要的自有动态库，减少第三方动态 Framework，对无动态加载需求的库优先考虑静态链接。

2. 减少 main 前自动执行代码  
   避免在 `+load`、constructor、C++ 全局对象初始化中执行耗时逻辑，把初始化改为懒加载、`dispatch_once` 或首屏后延迟执行。

3. 精简 Objective-C 元数据  
   删除无用类、方法、Category、Protocol，减少 Runtime 扫描和方法合并成本。

4. 控制动态性  
   避免为了灵活性引入过多启动期需要处理的动态行为。

5. 控制 Method Swizzling  
   避免在启动期大量 swizzle，必须做时也尽量轻量，或者延迟到对应子系统启用时再做。

### main

1. 轻量化首屏  
   让 `rootViewController` 只承担首屏必要职责，其他控制器和模块延后创建。

2. 避免主线程重任务  
   不在主线程做同步 I/O、网络阻塞、大解析、数据库和图片解码。

3. SDK 延迟初始化  
   只保留启动必要 SDK，其余能力按需初始化。

4. 优化布局  
   减少复杂视图树和频繁布局计算，稳定首帧渲染路径。

5. 优化首屏资源  
   控制图片、字体和配置资源大小，避免远程依赖阻塞首屏。

## 启动流程总结

从用户点击 App 图标开始，系统会先创建进程，按照 `Info.plist` 做基础配置校验，建立沙箱环境，然后显示 Launch Screen。

接下来进入 dyld 阶段，把可执行文件和依赖动态库加载进来，完成 ASLR 后的地址修正和符号绑定，随后 Objective-C runtime 开始注册类和分类，执行 C/C++ 全局构造器和 Objective-C 的 `load` 方法。

进入 `main` 之后，系统调用 `UIApplicationMain`，创建 `UIApplication`，启动主线程 RunLoop。到了 iOS 13 以后，通常还会进入 Scene 生命周期，在对应回调中配置 `window` 和根控制器。

随后首个控制器会依次触发 `loadView`、`viewDidLoad`、`viewWillAppear`，动画结束后调用 `viewDidAppear`，系统移除启动图，首帧内容正式呈现给用户。

理解这条链路之后，再回头看启动优化，思路就会清晰很多：

- pre-main 关注装载、链接、Runtime 初始化
- main 关注主线程任务、首屏渲染和业务初始化

最终目标不是“把所有事情都提前做完”，而是把真正影响首帧的事情压缩到最少。
